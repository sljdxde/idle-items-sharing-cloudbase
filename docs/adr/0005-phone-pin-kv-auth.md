# ADR-0005: 手机号 + 管理口令 + Cloudflare KV 替代「手机号即身份」

- **状态**：Accepted
- **日期**：2026-09-07
- **关联**：ADR-0001（薄代理持有 GitHub Token）、ADR-0004（已撤销的 PIN+HMAC 方案）
- **替代**：当前「输入手机号即登录，明文手机号存公开 Issue」体系

## Context（背景）

当前账号体系以「手机号即身份」为核心：用户输入 11 位手机号即登录，`localStorage` 持久化；写操作传 `operatorPhone`，Worker 仅做格式校验（`^1[3-9]\d{9}$`）后与 Issue 中的 `ownerPhone` 字符串比对。公开快照和 GitHub Issue 中存储明文 `ownerPhone` / `borrowedBy`。

这带来两个已确认的安全问题：

1. **明文手机号批量暴露**：公开快照 `items.json` 中所有用户的手机号可被一键下载，存在隐私泄露与骚扰风险。
2. **知道手机号即可冒充**：无任何第二因素验证，攻击者（或邻居）知道某人手机号后，输入即可登录并执行发布、删除、下架、冒领等所有写操作。ADR-0004 曾尝试用「6 位管理口令 + HMAC」解决，但因「用户忘掉一次性口令、换设备无法管理」被撤销。

用户提出新方案：用 `linli-` 开头的 24-30 位随机 token 替代手机号，通过「随机字符串 + 随机盐 + 纯前端双向加密」实现映射，管理员保留解密能力用于恢复。

经多维度评估（安全架构、前端实现、用户体验、数据迁移），该方案存在 5 个根本性缺陷：

- **纯前端没有真正的秘密**：对称加密密钥必然随 JS 代码泄露，加密等于编码，所有用户 token 可被一键批量解密。
- **登录无法校验存在性**：无后端数据库，任何格式正确的字符串都能「登录」，冒充门槛比手机号更低。
- **管理员万能钥匙与目标自相矛盾**：管理员可解密所有 token = 可冒充任何人，密钥一旦泄露 = 全部身份泄露。
- **24-30 位随机串对社区居民不可用**：预估 90 天遗忘率 60-75%，55 岁以上 80-90%，遗忘后物品变僵尸。
- **可逆加密与安全不可兼得**：要管理员可恢复就必须可逆，可逆就必须存密钥，密钥在前端必然暴露——逻辑闭环。

## Decision（决策）

**采用「手机号 + 6 位管理口令 + Cloudflare KV」方案（方案 A+）**，核心要点：

### 身份模型

- **手机号**仍是用户的主标识和登录凭证之一（用户不会忘，换设备可用），但不再明文存储在公开数据中。
- **管理口令（PIN）**是第二因素：注册时设置 6 位数字，登录时必须同时提供手机号 + PIN。PIN 的 bcrypt 哈希存储在 Cloudflare KV（不公开）。
- **公开标识**：Issue 和快照中存储 `ownerHash` / `borrowerHash`（`HMAC-SHA256(phone, HASH_PEPPER)`），不存明文手机号。

### 会话机制

- 登录成功后，Worker 签发 **7 天有效期的 JWT**（payload 含 `phoneHash`，用 `JWT_SECRET` 签名）。
- 前端存储 JWT 于 `localStorage`，写操作时通过 `Authorization: Bearer <jwt>` 携带。
- Worker 验证 JWT 签名和过期时间后，从 payload 提取 `phoneHash`，与 Issue 中的 `ownerHash` 比对执行鉴权。

### 存储位置

| 数据 | 存储位置 | 说明 |
|---|---|---|
| 手机号明文 | 仅前端 `localStorage`（本机） | 用于展示和登录传参，不进公开数据 |
| `phoneHash` | GitHub Issue（公开） | `HMAC-SHA256(phone, HASH_PEPPER)`，不可逆 |
| `pinHash` | Cloudflare KV（不公开） | `bcrypt(pin)`，自带盐，慢哈希防暴力破解 |
| `HASH_PEPPER` | Worker 环境变量 | 仅服务端可见，用于计算 phoneHash |
| `JWT_SECRET` | Worker 环境变量 | 仅服务端可见，用于签发和验证 JWT |
| `ADMIN_TOKEN` | Worker 环境变量 | 管理员重置 PIN 接口的鉴权凭证 |

### 管理员恢复

- 管理员通过 `ADMIN_TOKEN` 调用 `POST /api/admin/reset-pin`，传入用户手机号，Worker 计算 `phoneHash` 后从 KV 查到该用户，将 PIN 重置为临时值并返回。
- 管理员**无法查看**用户的原始 PIN（bcrypt 不可逆），只能重置。
- 管理员**无法冒充**用户（重置后用户需用临时 PIN 登录并修改，管理员不持有用户的 JWT）。

### 与 ADR-0004 的区别

ADR-0004 撤销的核心理由是「用户忘掉一次性口令、换设备无法管理」。本方案通过以下设计规避：

- PIN 是**用户自行设置**的 6 位数字（类似银行卡密码），不是系统分配的一次性随机串，用户有认知基础。
- 手机号仍是主标识，**遗忘 PIN 后可通过管理员重置**（管理员接口受 ADMIN_TOKEN 保护），不会永久锁死。
- 换设备只需手机号 + PIN 重新登录，与银行 APP 体验一致。

## Consequences（后果）

### 正面

- **冒充攻击被阻断**：知道手机号不足以登录，必须同时知道 PIN；PIN 哈希不公开，暴力破解受 bcrypt 慢哈希限制。
- **明文手机号不再暴露**：公开快照和 Issue 中只有不可逆的 phoneHash，隐私泄露风险消除。
- **用户体验变化小**：仍用手机号登录，仅多一步 6 位 PIN 输入；6 格分离输入框降低输入焦虑。
- **管理员恢复机制清晰**：可重置 PIN，不可逆（看不到原始 PIN），不可冒充（不持有 JWT）。
- **架构增量可控**：仅新增 Cloudflare KV（免费额度够用），不引入数据库或第三方服务。

### 负面 / 代价

- **用户需多记一个 PIN**：6 位数字，遗忘后需联系管理员重置；社区场景下可线下引导。
- **新增 Cloudflare KV 依赖**：需开通 KV 命名空间并绑定到 Worker，增加一个运维组件（尽管极轻量）。
- **历史数据需迁移**：现有 Issue 中的明文 `ownerPhone` / `borrowedBy` 需批量替换为 `ownerHash` / `borrowerHash`；老用户首次登录时需引导设置 PIN。
- **改造涉及面广**：Worker（5 个接口 + 安全原语）、前端（types/auth/api/LoginBox/itemOps/items store）、快照脚本、测试，预计 2-3 人日。

## 备选方案（被否决）

- **原 token 方案（linli- 随机串 + 纯前端加密）**：5 个根本性缺陷，安全性不升反降，UX 灾难。否决。
- **方案 A（JWT + 仅脱敏，无 PIN）**：1-2 人日即可落地，但「知道手机号即可登录」的冒充问题未解决——JWT 只是会话机制，不是身份验证。否决因核心安全问题仍在。
- **方案 C（仅脱敏，零改造）**：0.5 人日，但冒充问题和明文暴露问题均未解决，仅做表面功夫。否决。
- **方案 B（HMAC token + KV + 昵称）**：彻底消除手机号，5-8 人日，但用户需设置昵称且手机号仍需作为登录凭证，增量收益不抵额外复杂度。记为**未来升级路线**，当社区规模增长或有隐私合规要求时再评估。
- **WebAuthn / Passkey**：最高安全标准，但依赖设备支持（老年用户旧手机可能不支持），实现复杂度高。记为**长期方向**，当前阶段投入产出比低。
